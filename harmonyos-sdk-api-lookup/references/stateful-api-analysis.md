# 状态归属与恢复点分析

## 读取时机

功能查询涉及 setter/config、运行态对象生命周期、系统状态监听，或用户要求“设置保持”“恢复后同步状态”“外部状态变化”时读取本文件。

## 判断目标

不要只回答“有哪些 API”。需要判断状态属于谁、谁会改变它、什么时候会丢、恢复时应重新查询还是重新应用。

## 分析步骤

1. 识别状态归属对象：session、output、player、recorder、controller、connection、stream 或其他运行态对象。
2. 检查对象生命周期：是否存在 `create/open`、`release/close`、`recreate`、`start/stop` 等会替换对象实例的动作。
3. 判断设置保持方式：setter/config 改变运行态对象状态时，先缓存到插件自身状态，再在新对象配置完成后重新应用。
4. 判断外部可变状态：若状态可能被系统设置、其他应用、硬件、网络、权限或用户操作改变，同时寻找当前快照 API 和事件监听 API。
5. 给出恢复点：说明在对象重建后、应用恢复后、页面重建后、监听重新注册后，应重新查询或重新应用哪些状态。

## 判断规则

- 事件监听只能覆盖注册之后的未来变化，不能代表当前真实状态。
- 应用从后台回到前台、Ability 重新激活、页面重建、监听重新注册后，优先用 `get/is/query...` 类 API 重新查询当前快照。
- 重新查询后需要把最新状态推送给上层，不能等待下一次事件才更新 UI 或插件状态。
- 如果 SDK 只有事件没有快照 API，明确说明恢复后无法主动补偿当前状态，只能等待下一次事件。
- 用户设置依附于运行态对象时，保存期望值；新对象 create/open/configure 完成后、start/execute/load 前重新应用。
- 如果某项设置必须在特定生命周期阶段调用，在调用流程中标明恢复点，避免 start 后再设置无效。

## 反例检查

- 只在初始化时查询一次当前状态。
- 只注册监听，不在应用恢复后重新查询快照。
- setter/config 只调用运行态对象，不保存期望状态。
- 对象重建后直接 start/execute/load，未恢复用户设置。
- 把当前调用成功误认为后续重建后的对象仍然保持设置。
